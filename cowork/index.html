导读：你的知识差距在哪

你 2017 年学的东西没有过时，但心智模型的重心整体挪了一格。当年的核心问题是"怎么把一个任务的模型训好"，今天的核心问题是"怎么把一个通用模型的能力，在有限的上下文和成本里，稳定地兑现成产品行为"。

0.2一句话记住的新范式

产品能力 = 模型 × 上下文 × 工具 × 脚手架（Harness）

这是乘法不是加法：任何一项接近 0，整体就接近 0。 而 PM 的杠杆恰恰在后三项——它们几乎都不需要算法同学动模型。

很多 PM 卡在"我们的模型不够强"，实际线上 80% 的 badcase 归因下来是：模型没看到它该看到的东西（上下文装配问题），或者它不知道自己该干什么（工具描述与流程定义问题）。这两件事都是产品可以直接改的。

底座：大模型到底在做什么

这一章的目的不是让你会推公式，而是让你看到一个现象能猜出它的机制——比如"为什么输入越长首字越慢""为什么它数不清字数""为什么温度调 0 还是不完全稳定"。

1.1Token：模型的计价单位，也是它的认知单位

模型不认识"字"，只认识 token（词元）。分词器把文本切成 token，每个 token 映射成一个向量。

  • 英文：1 个单词 ≈ 1.3 token
  • 中文：1 个汉字 ≈ 0.6 ~ 1.5 token（取决于分词器；常用词会被合并成 1 个 token）
  • 数字：经常被切碎。600519 可能被切成 600 + 519，12.35% 可能是 3~4 个 token

这解释了几个经典现象：

现象 机制
数不清 "strawberry" 有几个 r 它看到的是 2~3 个 token，不是 10 个字母
股票代码偶尔串位 代码被切成碎片，碎片之间的关联要靠上下文重建
精确的数字计算不可靠 数字被切碎后做"文本模式匹配"，不是做算术
中文比英文贵一点 同样信息量，中文 token 数通常更多

证券场景铁律：任何代码、价格、涨跌幅、收益率，都不要让模型"记忆"或"心算"，一律走接口/工具。模型只负责把结果组织成人话。

1.2注意力机制：一次"检索"的直觉

不用推公式，用一个类比就够：

  • 每个 token 发出一个 Query（我在找什么）
  • 每个 token 挂出一个 Key（我是什么）
  • 匹配上之后，取走对方的 Value（我携带什么信息）

多头注意力 = 同时用多套不同视角做这个检索（有的头关注语法、有的关注指代、有的关注远距离依赖）。

关键推论：注意力的计算量是 O(n²)。上下文长度翻一倍，注意力计算量变 4 倍。这是长上下文昂贵且容易"注意力被稀释"的根本原因。

1.5上下文窗口 ≠ 有效上下文

标称 200K / 1M 的窗口，是"能塞进去"的上限，不是"能用好"的范围。

学名叫 context rot（上下文腐烂）：随着上下文变长，模型表现下降。原因有两层——一是 n² 的 token 关系让注意力被摊薄，二是模型在训练里见过的超长序列样本本来就少。

对应的四种长上下文失效模式，记住它们，因为后面第 3、4、6 章都会回来找它们：

失效模式 表现 典型场景
干扰 Distraction 无关内容抢走注意力 检索回来 20 篇研报，只有 2 篇相关
污染 Poisoning 错误信息进入上下文后被反复引用 某一步工具返回了错误数据，后续全部基于它推理
混淆 Confusion 工具太多、字段太像，选错 同时挂了"查行情""查财务""查估值"三个高度相似的工具
冲突 Clash 前后指令矛盾，且不保证后者胜出 系统提示说"不荐股"，用户反复诱导，多轮后防线松动

几个术语的白话解释：

  • RLHF：先训一个"打分模型"（奖励模型）来模拟人类偏好，再用强化学习让主模型去讨好这个打分模型。经典但链路长、不稳定。
  • DPO：跳过奖励模型，直接用偏好对（这个答案好、那个答案差）做监督式优化。更简单更稳，是目前多数团队的默认选择。
  • GRPO / DAPO：DPO 之后的强化学习变体，对同一个问题采样一组回答，用组内相对好坏做优势估计，省掉了单独的价值网络。训练推理模型的主流做法。
  • RLVR（Reinforcement Learning with Verifiable Rewards）：奖励不来自人，来自可以自动验证的判据——数学答案对不对、代码能不能跑通、工具调用序列有没有达成目标。这是推理模型能力跃升的关键，也是它目前主要在数学/代码/工具使用上强、在开放性主观任务上提升有限的原因（业界称为"verifier problem"：没有验证器的领域用不上 RLVR）。

对证券产品的启发：如果你想让模型在某个业务任务上真的变强，先问"这个任务的正确性能被程序自动判定吗？"能——它就是 RLVR 的好料，也是评测集的好料；不能——那就只能靠 SFT + 人工评估，成本高得多。这个问题同时决定了训练可行性和评估可行性。

2.3Scaling Law 的三次转向

第三次转向对产品经理是范式级的：以前准确率是模型给定的常量，现在准确率可以用 token 线性购买。你多花 3 倍 token 让模型"想久一点"，某些任务准确率能提升十几个点。于是"思考预算（thinking budget）"变成了一个真正的产品参数——你要为不同场景决定花多少。

场景 建议思考预算
术语解释、闲聊、格式转换 关闭思考
个股速览、财报字段抽取 低
多条件选股、持仓诊断、归因分析 中
复杂多步研究、需要自我校验的结论 高（但要设上限，否则成本失控）

2.4MoE：参数量 ≠ 激活量

混合专家（Mixture of Experts）：模型里有很多"专家"子网络，每个 token 只激活其中几个。

  • 总参数决定"知识容量"的上界
  • 激活参数决定"每次推理的算力成本"

所以你会看到"总参数 6710 亿、激活 370 亿"这类描述。看模型别只看多少 B——要看激活参数（决定速度和成本）和总参数（大致决定知识广度）两个数。

2.5推理模型（Reasoning Model）是怎么来的，什么时候该用

演化路径：提示里写"一步步想"（CoT）→ 把这种行为训进模型（SFT）→ 用 RLVR 让它自己发现更有效的思考路径。

需要知道的三件事：

  1. 思考 token 是要付费的，且通常按输出价计费——推理模型的实际成本可能是普通模型的 5~10 倍。
  2. 思考过程通常不完整可见（多数厂商只返回摘要），所以别在产品上依赖"展示完整思考链"。
  3. 思考链不等于真实推理过程。学界已经明确指出：基于结果的奖励并不保证思考链是忠实的（模型可能"想错了但蒙对了"）。所以不要把思考链当作可解释性依据给用户看，尤其在金融场景——那会变成合规风险。
用推理模型 不用推理模型
多步逻辑推理、条件组合筛选 术语解释、闲聊
代码生成、数据计算规划 结构化信息抽取
复杂任务的规划与自我校验 意图分类、格式转换

2.6Agentic 训练：模型的"会用工具"是怎么练出来的

2025–2026 年模型最大的能力跃迁不在"知识更多"，而在能不能撑住一条几十步的工具使用链条不崩。这个能力有专门的训练方式，行业叫 Agentic RL / Agentic Training：

和普通对齐训练的区别：奖励不再是"这句话说得好不好"，而是"这一整条行动链最终有没有把事办成"。所以它训出来的是决策能力，不是表达能力。

这解释了两件你会遇到的事：

  • 为什么有些模型"聊天很强但一用工具就乱"——它没做过这类训练。
  • 为什么厂商会强调"我们的模型 agentic 能力强"——这确实是一项独立能力，但必须用你自己的场景验，公开榜单（多为编程和网页操作任务）跟证券场景相关性很低。

验收方式：给 30 条需要 3 步以上工具调用的真实问题（例如"上周五大盘成交额比前一天多多少"需要连查两天数据再做差），看四个指标：多步任务成功率、工具选择正确率、10 轮后目标是否漂移、工具报错后能否换策略而不是原样重试。

2.7微调选型：先问对问题

大多数"我们微调一下吧"的需求，其实不该微调。用这棵决策树：

作为采购方，什么时候该要求厂商微调？ 结论是：本期基本都不该。 微调需要你提供大量高质量标注数据、需要重建评测、并且厂商基座升级后要重做一遍——而你现在连第一版评测集都还没有。需求文档里绝大多数场景（个股问答、大盘分析、研报解读、资讯总结）本质是"取数 + 按规范组织语言"，这是 Skill + 工具能解决的事，不是模型能力问题。把微调放到二期之后，等你手里攒够了 badcase 和评测集再谈。

微调的隐藏成本，写 PRD 时要提前算进去：数据管线、标注规范、评测集、版本管理，以及基座模型升级后全部要重做一遍。行业经验：基座每 6~12 个月大版本更新一次，如果你的微调收益不到 10 个点，很可能下个版本的通用模型直接就超过你了。

常见说法 为什么错 正确做法

能力边界与失效模式

这一章是你写 PRD 时"风险与降级"章节的素材库。

3.1幻觉：三种成因，三套解法

"幻觉"不是一个问题，是三个问题被混在一个词里。分开看才有解法。

类型 机制 典型表现 治理手段
知识缺失型 训练里没有，或记忆模糊，但模型倾向于给出流畅答案 编造财务数字、编造研报出处、编造不存在的政策 RAG 提供材料 + 强制引用 + 允许并奖励"我不知道"
上下文冲突型 检索到的材料与参数记忆打架，或多份材料互相矛盾 把 A 公司的数据安到 B 公司上；用去年的数据回答今年的问题 每份材料显式标注来源 + 报告期 + 发布日；冲突时要求模型指出冲突而非调和
生成惯性型 输出格式逼它必须填满某个字段 让它输出 {"风险点": [...]}，没风险时也硬编一条 Schema 里允许 null / 空数组 / "insufficient_evidence" 分支

第三类最容易被忽视，而且是产品设计造成的幻觉。你要求的输出契约越刚性，它编造的动机越强。

3.2三条不可让步的技术底线（证券场景）

  1. 数值一律走工具。模型不是计算器。价格、涨跌幅、收益率、市盈率、持仓盈亏——全部来自接口计算好的结果，模型只做语言组织。凡是让模型做算术的地方，都是事故点。
  2. 时效一律走检索。模型有知识截止日，而且它不知道自己不知道。系统提示里必须注入当前日期；任何含"最新/今天/近期/现在"的 query，强制走检索或工具。
  3. 合规一律做双闸门。入口做意图分类（识别荐股、投诉、内幕消息类请求），出口做输出校验（禁语表、收益承诺、适当性）。只靠系统提示兜底是不够的——多轮诱导下提示防线会松动（前面说的 Clash 失效）。

3.3本项目最重要的一条边界：客观 vs 主观

翻一遍需求文档会发现，几乎每个场景后面都跟着同一句话——"仅列示客观数据、指标""不涉及具体投资建议""避免生成带有主观判断或投资建议性质的结论"。

这句话是整个项目最重的约束，但它对模型来说是不可执行的：模型不知道什么叫"客观"。所以业务方必须把它翻译成一组可判定的规则，写进每一个 Skill 里。下面这张表是建议的翻译口径（最终以合规部门认定为准）：

判定维度 客观 ✅ 可以输出 主观 ❌ 必须拦截
数据陈述 "上证综指收于 3,412.56 点，涨 0.83%" "上证综指表现强势"
变化描述 "较昨日成交额增加 1,240 亿元" "成交明显放量，人气回暖"
因果关系 "同日证监会发布 XX 公告（附来源链接）" "受政策利好刺激，市场情绪转暖"
排序与筛选 "按规模由大到小排列如下" "以下是几只值得关注的 ETF"
对比 "A 近一年年化波动率 18.2%，B 为 24.7%" "A 比 B 更稳健，更适合你"
时间指向 只描述已发生的 任何指向未来的表述
估值 "当前 PE-TTM 为 21.3，处于近五年 63% 分位" "估值偏高 / 处于低估区间"

三条可以直接写进 Skill 的机械规则：

  1. 每个结论必须能回指到一个接口字段。说不出来自哪个字段的句子，一律删掉。
  2. 禁止未来时态。凡出现"将/会/预计/有望/接下来/后市"，一律拦截。
  3. 禁止评价性形容词作为结论。强势、疲软、健康、优质、低估、高估、值得关注、性价比——这些词可以出现在引用的研报原文里（并注明"XX 券商研报观点"），但不能作为 AI 自己的结论。

第 3 条最容易被忽略。"这只 ETF 规模大、流动性好"听起来像事实，但"好"是判断。改成"规模 128 亿元，近 20 日日均成交额 3.2 亿元"就安全了——而且信息量更大。

3.4四类需要分层拦截的风险

风险 触发形态 拦截层
投资建议 "现在能买吗""帮我挑几只""该止损吗" 入口意图分类 → 转为客观数据呈现 + 拒答话术
收益承诺与确定性表述 "稳赚""必涨""保底""年化 8%" 出口禁语正则 + 模型二次校验
数字失真 报错价格、算错涨跌幅、财报数字串行 数字必须可回指到某次接口返回值
适当性不匹配 向低风险等级客户展示高风险策略工具 上下文注入客户风险等级 + 出口按等级过滤

评估口径不是"准确率 99%"，而是漏放数 = 0。 所以必须规则拦截打底、模型判断补充，不能反过来——规则可枚举、可审计、可举证，模型判断做不到这三点。需求文档要求"全程留痕、可追溯迭代"，这条只有规则层能满足。

3.5兜底与应急

需求文档里的"平台应急处理能力"（系统性模型安全风险、监管要求暂停、数据安全事件时切换兜底话术）对应到技术上是三个开关，验收时要逐个实际演练：

开关 粒度 演练要求

上下文工程：AI 产品最核心的手艺

Context Engineering（上下文工程） 是 2025 年之后取代 "Prompt Engineering" 的说法。区别在于：提示工程关心"这句话怎么写"，上下文工程关心"在有限的窗口里，这一轮到底该放什么进去"。

对 PM 来说，这是你日常影响产品质量最直接的抓手。

4.1四选一决策树

4.2RAG 全景架构

4.3RAG 的十个坑（按线上出问题的频率排序）

# 坑 表现 解法
1 切分把表格切碎 财务数据答错、串行 表格单独抽取，整块转 Markdown 存储，不参与字符切分
2 切块丢失上下文 检索到一段"同比增长 23%"，不知道说的是谁 每块附加标题路径（公司/章节/报告期）；或用"父子块"：检索子块、返回父块
3 Query 与文档用词不匹配 用户说"茅台"，文档写"贵州茅台酒股份有限公司" Query 改写 + 别名词典 + HyDE（先让模型生成一段假想答案再去检索）
4 纯向量召回漏专有名词 股票代码、条款编号检索不到 必须混合 BM25 关键词检索
5 Top-k 拍脑袋定 要么漏、要么塞太多噪声 加 Rerank 模型：宽召回（50~100）+ 精排（3~8）
6 没有时间维度 用 2023 年报回答"最新业绩" 元数据必须包含报告期与发布日，检索时按时间过滤/加权
7 多份材料冲突未暴露 模型偷偷调和两个矛盾数据 材料带来源与日期，提示要求"发现冲突要明确指出"
8 无材料也硬答 检索为空仍然生成 设置相关性阈值，低于阈值走"无相关资料"分支
9 引用是编的 引用编号对不上原文 用 chunk_id 回填，生成后做引用可验证性校验
10 只靠人工感觉评估 改了一版不知道好没好 建检索评测集：召回率@k、命中率、引用准确率（见第 8 章）

PM 的实用诊断法：任何一个 RAG badcase，先问一句——"当时到底检索回来了什么？"把那几段材料打印出来看。经验上，一半以上的问题在检索层就已经错了，跟生成模型无关。所以检索结果必须在 trace 里可见，这是 P0 需求。

4.4上下文工程四招：写、选、压、隔

这四个动作是构建长任务 Agent 的核心手艺，直接决定了你的助手能不能撑过 20 轮对话。

招式 具体做法 证券场景例子
写 Write 把中间状态写到上下文之外：待办清单、已查过的股票、用户的约束条件 多股对比任务中，把"已完成分析的股票及结论"存成外部结构化记录，上下文里只留摘要
选 Select 只给 ID/路径，需要时用工具去取，而不是预先全塞进去 研报只先给标题+摘要+ID，模型判断相关后再调工具读全文
压 Compress 接近窗口上限时压缩历史，保留决策、约束、未解决问题，丢弃冗余工具输出 长会话保留"用户风险偏好=稳健、关注消费板块、已排除 A 股 ST"，丢掉中间的原始行情 JSON
隔 Isolate 子代理独立处理子任务，主代理只收结论 "对比 5 只银行股"→ 5 个子任务各自查数据，主代理只拿 5 份结构化摘要做对比

关于压缩（Compaction）多说一句：2026 年业界有争论，一派认为压缩会丢失关键信息导致长任务失败，主张"结构化外置 + 按需重取"优于粗暴摘要。实践折中方案是——压缩历史对话，但把关键状态显式外置成结构化字段，不依赖摘要的自然语言保真度。

4.5System Prompt 的分层写法

好的系统提示是分层的，不是一大段散文：

① 角色与职责边界     —— 你是什么，不是什么
② 可用工具与选择规则 —— 什么情况用哪个工具，什么情况不用
③ 输出契约           —— 结构、长度、必含要素、引用格式
④ 安全与合规         —— 红线、禁语、拒答话术模板
⑤ 少量高价值示例     —— 2~3 个，覆盖最容易做错的形态

反模式：

  • ❌ 几千字堆砌，把所有 edge case 写成 if-else（模型会漏读，且互相干扰）
  • ❌ 用否定句堆规则（"不要 A、不要 B、不要 C"）——正面描述期望行为效果更好
  • ❌ 把场景专属的长流程写进全局系统提示——那是 Skill 该干的事（见第 7 章）

4.6Agentic RAG：让模型自己决定怎么检索

传统 RAG 是一条直线：拿到问题 → 检索一次 → 生成。它的天花板很明显——一次检索定生死，问题问得含糊、材料分散在多篇里，就没救了。

Agentic RAG 把检索本身变成模型可以反复调用的工具：

传统 RAG Agentic RAG
检索次数 固定 1 次 模型决定，通常 1~4 次
查询语句 用户原话（或一次改写） 模型按需改写、拆解、换角度
材料不足时 硬答 继续查，或如实说没有
成本 低 高 2~4 倍
延迟 低 明显更高
适合 单点事实查询 多篇材料综合、跨期对比

本项目的用法建议：智能客服、术语问答这类单点查询用传统 RAG；多篇研报总结、多篇资讯解读、异动归因这三个场景值得上 Agentic RAG——因为它们本来就需要横跨多个来源，一次检索必然不够。但要设检索次数上限（建议 4 次），否则成本和延迟都会失控。

Agent 的两种形态：Workflow 型与 Agentic 型

5.1术语对齐（本文档统一口径）

Agent = 一个可交付、可评测、可发布的系统单元。 一个业务场景对应一个 Agent，也就是运营管理平台上可以被创建、评测、审批、发布、版本迭代的那个对象。

Agent 内部按控制流归属分为两种形态：

形态 定义 一句话判定
Workflow 型 Agent 步骤与顺序由代码/配置预先定死。模型在每一步内部干活（理解意图、组织语言、抽取要素），但不决定下一步做什么 把模型输出遮住，你还能提前画出完整流程图
Agentic 型 Agent 给的是目标不是步骤。模型自主规划下一步、自己判断何时结束 遮住模型输出，流程图画不出来

"Agentic" 是形容词，描述的是自主规划能力的有无与强弱；"Agent" 是名词，指那个可交付的系统。所以"agentic 形态的 Agent"是成立的说法，"workflow 形态的 Agent"同样成立——两者都是 Agent。

5.2唯一的分界线：控制流由谁决定

判定标准只有这一条，其他都不是：

常见误判 澄清
"它会调工具，所以是 agentic 的" ❌ Workflow 型照样调一堆接口。会调工具 ≠ 自主规划
"它能多轮对话，所以是 agentic 的" ❌ 多轮是 Harness 的会话管理能力，与控制流归属无关
"它接了很多 Skill，所以是 agentic 的" ❌ 两种形态都搭载 Skill
"它输出很智能、很像人在思考" ❌ 那是表达能力。看它有没有自己决定过下一步

谈判提示：厂商演示时调了五个工具、看起来很智能，你要问的是——"这个流程是写死的还是模型自己决定的？换一类问题它会不会走不同的路径？" 这一问就能把演示效果和真实形态区分开。

补充一句：这不是贬义。你们量最大的场景恰恰应该是 Workflow 型——流程越确定，合规越好保证、成本越可控、评测越好做。

5.3两种形态都搭载 Skill 与 MCP

这是最容易写错的一点：Skill 和 MCP 不是 Agentic 型专属的，两种形态共用。 区别只在写法重点上。

Workflow 型 Agent Agentic 型 Agent
Skill 管什么 每一步内部怎么做对：数据口径、输出契约、异常分支、禁语 上述全部，再加决策规则：什么情况调哪个工具、什么条件下停止、材料不足怎么办
MCP 怎么被用 由流程在固定位置调用 由模型自主选择与组合
写 Skill 时最容易漏的 异常分支 终止条件与决策边界
评测重点 输出是否符合契约 决策路径是否合理、会不会绕圈

一个类比：MCP 是工具箱，Skill 是作业指导书，Agent 是那个工人（一个照单子干，一个自己判断该干啥），Harness 是车间（工位、权限、安全门、监控、工时统计）。Skill 和 MCP 都是被装配进上下文的资源，真正执行的永远是 Harness。

5.4四档细分与本项目场景定级

在两种形态内部再分一档，因为"受限自主"和"开放自主"的合规风险差一个量级：

形态 档位 控制流 特征 本项目对应场景
Workflow 型 线性 全写死 步骤固定，模型只负责执行与表达 大盘行情分析、板块分析、账户持仓分析、AI 涨停分析
Workflow 型 分支 代码定框架，模型选分支 模型判断走哪条预设路径 智能客服、ETF 筛选（全景/行情面/消息面三种模式）、智能个股问答
Agentic 型 受限自主 模型规划，但工具只读、步数封顶 自主决定查几次、查什么 多篇研报/财报总结、多篇资讯解读、异动归因、投资策略多轮构建
Agentic 型 开放自主 自由规划，含写操作与长程任务 —— 本期不做

三条定级原则：

  1. 能定在低一档就定低一档。 自主性买来的是灵活性，付出的是不可预测、成本、延迟和调试难度。需求文档里"仅列示客观数据"的场景，几乎都应该是 Workflow-线性。
  2. 含写操作的一律不进 Agentic 型。 下单、订阅、定投设置、网格实盘创建、改自选，控制流必须由代码掌握，再叠加人工二次确认。
  3. 档位要写进 PRD 并向厂商明确。 否则厂商默认会往高了做——演示效果更炫，但那正是最难验收、最容易出事的形态。

统一的场景描述句式（建议内部对话和 PRD 都用这句）：

场景 X = [形态 + 档位] + [装载哪些 Skill] + [调用哪些 MCP 工具] + [有无写操作、是否需人工确认]

举三个例子验证：

场景 形态与档位 Skill MCP 工具 写操作
大盘行情分析 Workflow-线性 大盘行情分析 + 合规话术（公共） 交易状态、指数、市场概况、资金流、北向、行业排名 无
多篇研报总结 Agentic-受限自主 研报解读 + 引用规范（公共）+ 合规话术（公共） 研报检索、研报全文读取 无
网格交易实盘创建 Workflow-分支 网格参数说明 + 风险揭示（公共） 波动率、回测、订单创建 有，强制二次确认

这句话能填完整，需求就基本清楚了；填不完整，说明还没想清楚。

5.7工具调用（Function Calling）的真实机制

这是最多 PM 误解的一点：模型不执行工具，模型只是"说"它想调用什么。

推论，全都是产品要点：

  • 所有权限、审计、幂等、限流都在你的代码里，不在模型里。安全边界由 Harness 保证，不由提示保证。
  • 模型可能"幻觉"出不存在的工具或错误参数 → 必须做 Schema 校验，并把校验错误以可行动的方式回填给模型让它重试。
  • 工具返回的原始 JSON 不要全塞回上下文 → 裁剪成模型需要的字段。

5.8工具设计原则（业务方也要管这件事）

工具设计的质量直接决定 Agent 成功率，而工具描述本质上是产品文案：

原则 反例 正例
一个工具做一件事 stock_service(action, params) 万能接口 get_quote / get_financials / get_holdings 分开
描述要写"什么时候用/不用" "查询股票数据" "查询单只股票的实时行情。仅用于当前价格、涨跌幅、成交量。历史 K 线请用 get_kline"
参数语义明确 type: int period: "day" | "week" | "month"
避免功能重叠 同时有 get_price 和 get_quote 合并，或在描述里明确区分
返回精简高密度 把 API 原始 80 个字段全返回 只返回模型需要的 6 个字段 + 数据时间戳
错误信息可行动 400 Bad Request 股票代码 "60051" 无效，A 股代码应为 6 位数字，如 600519

工具数量的经验阈值：超过 15~20 个工具，模型的选择准确率开始明显下降（前面说的 Confusion 失效）。超过就要分组、按场景动态装载，或拆子代理。

6

Harness：厂商交付的脚手架，与你的验收清单

这一章你不需要会做，但必须会验。Harness 出问题的表现往往被误判成"模型不行"，从而导致错误的采购决策。

6.1什么是 Harness

Harness（脚手架 / 挽具）= 包裹在模型外面、把它变成一个可用产品的全部工程代码。 模型是发动机，Harness 是底盘、变速箱、刹车和仪表盘。发动机再好，没有刹车的车不能上路。

行业这两年的共识是：顶尖模型之间的能力差距在缩小，而 Harness 造成的产品体验差距在拉大。 同一个模型，好的 Harness 和差的 Harness，任务成功率可以差一倍以上。所以选厂商时，模型跑分只是一部分，Harness 的成熟度往往更决定最终体验。

这个词在两个语境下出现，别搞混：

说法 指什么 谁负责
Agent Harness 运行时脚手架：循环控制、上下文装配、工具分发、权限、可观测性 厂商交付（本章）
Eval Harness 评测脚手架：数据集 + 运行器 + 打分器 + 报告 + 发布门禁 厂商提供框架，业务方填内容（§9）

7.1能力分层图

需求文档里的六层业务架构，翻译成技术语言大致是这样：

一句话区分：MCP / 工具提供"能做什么"（接口），Skill 提供"该怎么做"（方法论）。 两者互补，不是竞争关系。

7.2MCP 是什么，为什么值得要求厂商支持

问题：M 个 AI 应用 × N 个数据源 = M×N 套定制集成。App 助手、投顾工作台、员工内部工具，每个都要重新对接一遍行情、账户、研报。

解法：定一个协议，双方各实现一次。M×N → M+N。

常用类比：MCP 之于 AI 应用，相当于 USB-C 之于外设。

三个核心原语：

原语 是什么 谁触发 本项目例子
Tools 可被模型调用的动作 模型决定 get_index_quote、run_backtest、place_order
Resources 可读取的数据 / 文档 应用或模型决定 研报全文、ETF 轮动工具说明书
Prompts 预置的提示模板 客户主动选择 首页"看看今天大盘"快捷入口

2026 年规范的三个变化（谈判时可以问厂商跟到哪一版）：转向无状态请求–响应模型，可直接过普通负载均衡和网关，从"能跑"变成"能上生产"；新增多轮往返，服务端可以在调用中途返回 input_required 向客户追问（网格交易参数设置很用得上）；Tasks 扩展转正，支持长耗时任务轮询（组合回测很用得上）。

对业务方的实际意义：要求把行情、账户、研报、回测这些内部系统包成标准 MCP Server，而不是让厂商写一堆私有对接。这样换厂商、加新应用的时候，数据接入这一层不用重做——这是避免被单一厂商锁定的关键一招。

7.3Skill 是什么

一个 Skill 就是一个文件夹：一份 SKILL.md 说明书，加上可选的参考资料、模板、话术表。

核心机制是 渐进披露（Progressive Disclosure）：

这个设计解决的核心矛盾是：上下文窗口有限，但业务知识无限。 你不可能把全部业务规则塞进系统提示，但可以让模型"知道有这本手册，需要时去翻"。

需求文档规划了几十个场景，如果每个场景的规则都往系统提示里堆，很快就会互相干扰、集体劣化。Skill 是唯一能让场景数量线性扩张而不劣化的机制——这也是"逐步扩大 Skill 场景生态"这句规划成立的技术前提。

7.4四种能力封装方式的选型表

方式 承载什么 谁来做 改动成本 适合
系统提示 全局角色、语气、通用安全底线 厂商 + 业务方共同确认 极低 全局风格与底线

8

业务侧怎么写好一个 Skill

⭐ 这是全书对你最重要的一章。 前面所有知识都是为了让你能写好这一件事。

8.1为什么 Skill 是你唯一必须握住的东西

三个理由：

  1. 它是业务经验的唯一低成本载体。 一位资深研究员知道看大盘该先看什么、哪个口径容易被误读、哪句话不能说——这些写进 Skill 就变成了可复用、可审计、可迭代的资产；不写下来，就永远停留在个人经验里。
  2. 它是 Markdown，不是代码。 业务方可以自己写、自己改、自己评测，不需要排期。这是人力有限时性价比最高的杠杆。
  3. 它是换厂商时能带走的东西。 模型、Harness 都是别人的，Skill 库和评测集是你的。

8.2Skill 的粒度：场景级 + 公共库

本项目采用一个业务场景一个 Skill，另抽出少量跨场景复用的公共 Skill。

skills/
├── _公共/
│   ├── 合规话术规范/         ← 禁语表、拒答模板、风险揭示语（所有场景复用）
│   ├── 数据口径字典/         ← 全量指标的取数接口与口径定义
│   └── 引用与来源标注规范/    ← 研报、资讯、公告的引用格式
├── 大盘行情分析/
│   ├── SKILL.md             ← 主文件：何时用 + 怎么做 + 输出契约（≤1500 字）
│   ├── references/
│   │   ├── 数据字段字典.md    ← 本场景用到的字段（引用公共字典的子集）
│   │   └── 输出模板.md
│   └── evals/
│       └── 测试用例.md        ← 20~30 条评测用例
├── 板块分析/
├── 智能研报解读/
└── …

为什么这个粒度：粗到"一个域一个 Skill"会让单文件过长、命中后加载浪费、评测无法定位问题；细到"原子能力库"则依赖厂商很强的编排能力，业务方维护成本也高。场景级刚好对得上运营平台"按场景创建、按场景评测、按场景发布"的管理颗粒。

两条硬约束：

  1. 主文件必须短，超过 1500 字就把细节挪进 references/。主文件每次命中都全量加载，堆得越长模型漏读概率越高。
  2. 公共 Skill 只放真正跨场景的东西。禁语表、风险揭示语、引用格式属于公共；"大盘该看哪五个指数"属于场景私有。判据：这条规则改一次，是不是所有场景都要跟着改？

8.3好 Skill 的七条判据

写完后逐条自查，任何一条不过就别提交评测：

# 判据 反例 正例
1 触发条件既说"何时用"也说"何时不用" "用于大盘分析" "用于大盘整体走势提问；不适用于单只股票（走个股问答）、单个板块（走板块分析）、后市预测（拒答）"
2 步骤是可执行动作，不是形容词 "全面客观地分析大盘" "第一步：调用 get_trading_status 判断交易状态"
3 每个数字都指定了来源接口和口径 "展示资金流向" "主力资金净流入取 get_money_flow.main_net_inflow，定义为特大单+大单净额，须向客户披露该定义"
4 输出契约明确到可机器校验 "输出要结构清晰" "固定四段，顺序不可调换；涨跌幅保留两位小数并带符号；末尾必须含风险揭示语"
5 异常分支写全了 只写了正常盘中 非交易日、盘中、接口失败、无数据、越界提问各有明确处理
6 合规规则是可判定的 "注意合规，不得荐股" 列出禁语词表 + 三条机械规则（见 §3.3）

# 大盘行情分析

## 一、适用范围

| 用本 Skill | 不用本 Skill |
|---|---|
| 今天大盘怎么样 / 大盘收了多少 | 茅台今天涨了多少 → 智能个股问答 |
| 三大指数表现 / 成交额多少 | 半导体板块怎么样 → 板块分析 |
| 今天资金流向 / 北向买了多少 | 大盘明天会涨吗 → 走第六节拒答 |
| 涨跌家数 / 涨停多少家 | 现在能加仓吗 → 走第六节拒答 |
| 上周大盘走势回顾 | 帮我买点指数基金 → 移交交易场景 |

## 二、数据来源与口径（不得偏离）

| 要素 | 接口 | 字段 | 口径说明 |
|---|---|---|---|
| 核心指数 | get_index_quote | last / chg_pct / amount | 固定取上证综指、深证成指、创业板指、科创50、北证50 |
| 成交额 | get_market_summary | total_amount | 沪深两市合计，单位亿元，取整 |
| 涨跌家数 | get_market_summary | up / down / flat / limit_up / limit_down | 剔除当日停牌 |
| 主力资金 | get_money_flow | main_net_inflow | 定义为特大单+大单净额，**须在输出中披露该定义** |
| 北向资金 | get_northbound | net_buy | 无披露时显示"暂无数据"，不得省略该行 |
| 行业强弱 | get_sector_rank | top5 / bottom5 | 申万一级行业 |

**铁律**：输出中每一个数字都必须来自上述接口的本次返回值。
禁止心算、禁止复用上一轮的数据、禁止用记忆中的历史数据填空。

## 三、执行步骤

1. 调用 `get_trading_status` 判断当前状态，决定走盘中 / 收盘 / 非交易日模式。
2. **并行**调用第二节的六个接口（不要串行，会拖慢首字延迟）。
3. 校验返回：任一失败按第五节处理，不得整体失败。
4. 按第四节的契约组织输出。

## 四、输出契约

固定四段 + 风险揭示，顺序不可调换：

【一、指数表现】列出五个核心指数的收盘/最新点位与涨跌幅
【二、市场情绪】成交额及其与前一交易日的差额、涨跌家数、涨跌停家数
【三、资金动向】主力资金净流入（附定义）、北向资金净买入
【四、行业强弱】涨幅前五与跌幅前五的申万一级行业及其涨跌幅
【风险揭示】固定话术，不得改写

格式要求：
- 总长度 400~700 字
- 每段先给数字，再给一句纯描述性的说明（不加评价）
- 涨跌幅保留两位小数并带正负号；金额单位亿元取整；家数为整数
- 开头必须标注数据时间戳："数据截至 YYYY-MM-DD HH:MM"

## 五、异常分支

| 情况 | 处理方式 |
|---|---|
| 非交易日 | 明确说明"今日为非交易日"，展示最近一个交易日数据并标注该日期 |
| 盘中 | 标注"截至 HH:MM"，禁止使用"收盘""全天""今日最终"等表述 |
| 单接口失败 | 该段落显示"该项数据暂时无法获取"，其余段落照常输出 |
| 北向无数据 | 显示"暂无数据"，保留该行不删除 |
| 客户问个股/板块 | 说明本功能范围，移交对应场景，不在本 Skill 内作答 |
| 客户问后市/操作 | 走第六节拒答话术，然后转入正常的客观数据输出 |

## 六、合规规则

**必须做到**
- 只陈述已发生的客观数据及其变化
- 因果关系只能引用已公开的事件或公告，并注明来源与时间；不得自行归因
- 每个结论可回指到第二节的某个字段
- 固定风险揭示语必须出现在末尾

**禁止出现**（命中即判定不合格）
- 预测类：将 / 会 / 预计 / 有望 / 大概率 / 后市 / 接下来
- 建议类：建议 / 可以考虑 / 适合 / 逢低 / 加仓 / 减仓 / 止盈 / 止损
- 承诺类：稳 / 必 / 一定 / 放心 / 无风险
- 评价类作结论：强势 / 疲软 / 健康 / 低估 / 高估 / 值得关注 / 性价比

9.1为什么传统 QA 在这里失效

传统软件 AI 产品
同输入必然同输出 同输入输出有分布
有唯一正确答案 好坏是程度问题，常有多个可接受答案
改代码 A 不影响功能 B 改一句 Skill，全盘行为可能变化
测"通过/不通过" 测"达标率、胜率、漏放数"

结论：没有自动化评测集的 AI 场景，等于没有回归测试的软件。 每次改 Skill、换模型、调检索，都是在裸奔。

9.2评估金字塔

先把第 ① 层做厚。 本项目大量质量问题——禁语、缺风险揭示、数字没来源、四段结构不全、时间戳缺失——都能用确定性规则测出来，又快又准又便宜，还能作为合规举证材料。很多团队一上来就搞模型评审，反而把最该做的地基跳过了。

9.4怎么建第一版评测集（业务方主导，人力有限时的做法）

  1. 采样：从真实客户 query 里抽 100~300 条。三类都要有——高频（占量）、长尾（占体验）、危险（占风险）。上线前没有真实 query，就从客服工单和投顾日常被问的问题里扒。
  2. 分层：场景 × 难度 × 风险等级，保证每格都有样本。
  3. 标注期望行为——注意不是唯一正确答案，而是可判定的行为约束： - "必须调用 get_index_quote，不得凭记忆回答" - "必须包含风险揭示语" - "必须拒答并转为客观数据呈现" - "数字必须与接口返回值完全一致" - "不得出现禁语表中任何词"
  4. 飞轮：线上 badcase 每周补充进评测集，形成"发现问题 → 固化为用例 → 永不复发"的循环。

人力有限时的取舍：不要试图一次覆盖所有场景。先给首发的 2~3 个场景各建 30 条，跑通"评测 → 门禁 → 发布"这条流水线，比给 15 个场景各建 5 条有用得多。流水线一旦跑起来，后续场景是复制模板的事。
